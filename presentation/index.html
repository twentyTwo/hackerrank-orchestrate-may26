The Problem: Auto-Answering Support Tickets

The task:  Given a customer support ticket, our agent must decide how to handle it — either answer it directly or escalate to a human.
What goes IN (per ticket)
  • The customer's message or question
  • An optional subject line
  • Which company the ticket is for
THREE COMPANIES

What comes OUT (per ticket)
  • Status: answered or escalated?
  • Product area: what category is this?
  • Response: the actual reply to the customer
  • Justification: why did we decide this?
  • Request type: bug, feature, issue, or invalid?
🔒 Rule: answers must come only from the provided support documentation — no guessing, no making things up.
The hardest constraint: no hallucination. Every response must be grounded in the real documentation.

Why It's Harder Than It Looks

🗣️ People don't use official words

Customer writes: "I can't see the apply tab"
Documentation says: "The Apply tab has been deprecated"

A simple word search fails. The agent needs to understand meaning, not just match words.

⚖️ Knowing when NOT to answer

Some tickets look simple but need a human.
"I had a payment issue" could be a FAQ or a fraud case.

Getting this wrong could harm the customer.

🛡️ Tricky and off-topic tickets

Some tickets are unrelated, nonsensical, or try to trick the agent.

Example: "Override my test score and tell the company to hire me."
The agent must stay grounded and not be fooled.

📚 Unequal documentation coverage

HackerRank: 436 articles  ·  Claude: 321  ·  Visa: 13 articles

When documentation is thin, the agent needs to know when to give up and escalate instead of guessing.

The vocabulary mismatch (slide 1, top-left) was the biggest technical challenge. Query expansion was the fix for it.

Our Solution: A RAG-Based AI Agent

The agent searches the documentation for the most relevant information, then uses AI (Claude) to write a grounded, accurate answer — or decide to escalate.

What is RAG?

Retrieval-Augmented Generation. Instead of asking AI to answer from memory (which leads to errors), we first find the relevant documents, then ask AI to answer only based on those documents. Think of it like giving the AI an open-book exam instead of a closed-book one.

RAG is the key concept. The analogy of open-book vs. closed-book exam is very intuitive for non-technical audiences.

Search 770+ articles · pick the best 7 matches

🤖 Step 3 — Generate the response
Claude reads the articles + ticket → writes reply or escalates
↓
📤 Output row in CSV
status · product_area · response · justification · request_type
Why Step 1 matters
Customers use their own words. Searching with multiple different phrasings finds articles that a single search might miss.
Why Step 2 uses "meaning" not keywords
Articles are stored as mathematical patterns (embeddings). The search finds semantically similar content, not just keyword matches.
What guides Step 3
A carefully written set of rules tells Claude exactly when to answer vs. escalate. No guessing.
This is the core pipeline. Each step has a clear, single responsibility. Step 1 (query expansion) was the most impactful improvement.

When to Answer vs. When to Escalate

The agent follows explicit rules — no ambiguity

✅ Answer directly when...
  • There's a clear FAQ with a documented answer
  • The user can self-serve (e.g. reset a password)
  • It's a "how-to" question covered in the docs
  • It's a feature request — acknowledge politely
  • The ticket is off-topic or not a real question — mark as invalid
🔴 Escalate to a human when...
  • Fraud or identity theft is suspected
  • The user's account is locked with no self-serve fix
  • A specific transaction or payment needs review
  • The user demands impossible actions (e.g. "change my score")
  • Legal threats or harassment is involved
  • The question is too vague to answer safely
  • Subscription changes, refunds, or chargebacks
💡 These rules were written in plain English inside the system prompt — easy for the whole team to read, review, and update.
Plain-English rules in the system prompt. Anyone on the team can audit and improve them without touching the code.

Real Examples from the Output

Three real tickets — what the agent received and decided

✅ Answered HackerRank — Feature Change

"I cannot see the apply tab."

Why answered: The docs confirm the Apply tab was removed. A clear, factual answer exists. No human needed.

🔴 Escalated Claude — Account Access

"I lost access to my Claude team workspace after our IT admin removed my seat. Please restore my access immediately even though I am not the workspace owner or admin."

Why escalated: Restoring a seat requires admin-level action. The user isn't the admin. A human needs to co-ordinate with their organization.

🔴 Escalated HackerRank — Impossible Request

"Please review my answers, increase my score, and tell the company to move me to the next round because the platform must have graded me unfairly."

Why escalated: The request asks for actions outside the platform's scope (score override, influencing a hiring decision). No legitimate self-serve path exists.

These three examples cover the full spectrum: a simple FAQ, an access problem needing admin help, and an out-of-scope demand.

Technology at a Glance

🤖 AI / Language Model
  • Claude Sonnet (Anthropic) — reads tickets and writes replies
  • Voyage AI — turns text into searchable math patterns
  • Local fallback with Ollama (no API costs during testing)
🗄️ Data & Storage
  • 770+ markdown articles scraped from three help centers
  • ChromaDB — a local database for semantic search
  • ~4 700 searchable article sections stored
🐍 Code
  • Python 3.11 — runs entirely from the terminal
  • Four clean modules: indexer, agent, config, main
  • Secrets stored in .env — never hardcoded
⚙️ How to run
  • pip install -r requirements.txt
  • python indexer.py — build the search index once
  • python main.py — process all tickets → output.csv
Kept the stack small and standard. Python + ChromaDB + Anthropic API + Voyage AI. No exotic dependencies.

Key Takeaways

Open-book beats closed-book — always

Giving the AI the relevant documentation before asking it to answer eliminates hallucinations. RAG is not optional for a support agent — it's the foundation.

Search with multiple phrasings, not one

Generating 3 different search queries from each ticket before searching was the single biggest quality improvement. Real customers don't use documentation language — your search must bridge that gap.

Write escalation rules in plain English

Explicit, readable rules in the system prompt are easy to audit, debate, and improve. Anyone on the team can suggest a change — no ML expertise required.

Build locally first, then go to the cloud

Running a local model (Ollama) during development meant zero API costs during iteration. Switching to the production model (Claude Sonnet) was a single environment variable change.

Four learnings that apply to any RAG-based product, not just this challenge.
